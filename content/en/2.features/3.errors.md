---
title: Frontend Error Monitoring
description: Understand automatic error capture, context, deduplication, rate limits, and reporting handled business failures.
---

Frontend errors happen in the user’s browser and may never reach server logs. The PulseWatch SDK captures common failures from global exceptions, resource loading, and request flows, adding enough page context to investigate.

## Automatic capture

| Type | Source | Example |
| --- | --- | --- |
| `js_error` | `window.error` | Undefined function or runtime exception |
| `promise_error` | `unhandledrejection` | Unhandled Promise rejection |
| `resource_error` | Resource error event | Script, CSS, or image load failure |
| `api_error` | Fetch / XMLHttpRequest | Network failure or HTTP 4xx/5xx |

The SDK excludes its own reporting requests to prevent recursive monitoring failures.

## Context and safeguards

A record may include the error name, message, stack, URL, path, visitor/session/page-view identifiers, environment details, and recent click or route breadcrumbs. Click breadcrumbs include only the element tag, ID, and up to two classes—never its text or input value.

Duplicate errors are suppressed briefly, and each client has a per-minute reporting limit. These controls reduce error storms but do not replace fixing the root cause.

## Report a handled error

```js
try {
    await saveProfile()
} catch (error) {
    await window.PulseWatch.captureError(error, {
        module: 'profile',
        operation: 'save'
    })
}
```

Do not include passwords, tokens, complete forms, or unfiltered server responses in extra data. See [Privacy and Collection Boundaries](/sdk/privacy).
